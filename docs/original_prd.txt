Background
Current driver registration is messy and time-consuming in the driver app, and the Compliance team struggles to verify applicants efficiently. The process creates delays, inconsistent encoded data, and repeated back-and-forth when documents are unclear or incorrect. We need a simpler onboarding flow that reduces driver effort, standardizes verification/encoding on the web, and speeds up endorsement for activation while still supporting reupload loops and training-center guidance during verification.
Based on observation drivers who newly installed the driver app takes them 30 minutes to an hour to finish the submission of requirements in the app. This is a burden to both drivers and compliance team.

---
Objective
Simplify driver onboarding from account creation to activation by:
- Streamlining the mobile app into a guided, required-only flow up to Submit for Review
- Providing a web verification portal where Compliance can review, correct typos (except mobile number), encode key information from documents, approve/reject with reasons, and set application source
- Supporting a clean reject → reupload → resubmission → reverify loop
- Allowing applicants to visit training centers even while verification is ongoing via an in-app training center list and help contact number

---
Target Audience
Driver Applicants (2W / 4W): need a fast, guided registration and clear reupload instructions when documents are rejected
Compliance / Verifiers: need a shared queue, document viewer, structured encoding fields, reject reasons, and endorsement gating
Mobility / Ops Admins: maintain training center schedules/contact details and ensure smooth activation handoff

---
Measure of Success
Cut down driver registration time (account creation → submit for review) from 30mins to an hour to 5–10 minutes.
Cut down compliance happy flow time (open applicant → endorse for activation) to 5–10 minutes for clean applications.

Scope and Out of Scope
Mobile App Scope (Driver App)
1. Account Creation (OTP)
- Mobile number entry → request OTP → OTP entry screen.
- OTP UX enhancement: remove “Verify” / manual verification button.
  - Auto-advance to the next step once 6 digits are entered and the OTP is correct.
  - Show inline error for incorrect OTP and allow re-entry.
  - Keep OTP timer/expiry behavior and “Change Number” option.
2. Personal Details (Required)
- Full name
- Date of birth
- Full address
- Email address
- Emergency contact name
- Emergency contact mobile number
- (Mobile number remains the signup identifier / non-editable after account creation)
3. Vehicle Type Selection (Required)
- Select 2W or 4W (drives required document checklist + conditional requirements).
4. Service Selection (post vehicle type)
- Show: Ride, Send, Eats, Mart
- Non-Ride services may be visible but disabled (backend-configurable for future enablement without app update).
5. Document Upload (Required + Conditional)
- Required document slots based on vehicle type + rules:
  - Driver’s License (Front + Back)
  - OR/CR (+ conditional ownership supporting docs)
  - NBI
  - Vehicle Photos (Front + Back)
  - PA/CPC (4W only)
  - Fit to Drive (conditional by age + vehicle type)
  - Previous App Experience proof (if present in the flow/prototype)
- Upload rules:
  - Multi-file per slot (front/back, multi-page)
  - Accepted: JPG / PNG / PDF
  - Max size: 8MB per file
  - Block submission until all required/conditional slots are completed
6. Document Guides w/ Info Icons (NEW)
- Every document type must have an info (ℹ️) icon that opens a guide panel/modal containing:
  - Clear do/don’t instructions (photo clarity, angle, completeness, expiry visibility, etc.)
  - Example images (good vs bad samples) per document type
- Guides are view-only and accessible before upload (to reduce rejection loops).
7. Submit for Review
- Single action submits application and moves status to Pending Review / Pending Verification.
8. Pending Review Status Screen (View 6) — Read-Only Submission Summary (NEW)
- Show “Application Submitted / Pending Review” status messaging.
- Read-only submission summary: display a complete list of all uploaded documents (all slots + files).
- Click-to-view (NEW): each file name is clickable to open the actual uploaded image/PDF in a viewer.
- Viewer is strictly read-only (no replace/delete/upload from this screen).
- Training Centers list + Support/Help contacts remain visible here.
9. Rejected → Reupload Flow
- If Compliance rejects any document slot:
  - Status becomes Needs Document Reupload
  - Show rejected document(s) + reason(s)
  - Allow reupload only for rejected slots (same upload rules)
10. Resubmitted Successfully Screen (View 8) — Read-Only Submission Summary (NEW)
- Confirmation messaging that documents were resubmitted.
- Same read-only submission summary behavior as View 6:
  - List all uploaded docs/files
  - File name click opens read-only viewer (no modification)
- Training Centers + Support/Help contacts remain accessible.
Web Scope (Compliance / Mobility Portal)
- Applicant Work Queues (Tabs)
  - New: all newly submitted applicants pending initial verification
  - My Applications: shared “in-progress” list (no claiming)
  - Rejected: all applicants with rejected documents / needs reupload
  - Resubmission: applicants who reuploaded and resubmitted documents for review
- Shared Queue Model (No Claiming)
  - All compliance users can see all applicants in all tabs
  - Any compliance user may continue processing an application previously handled by another compliance user
- Audit Visibility
  - Each tab table includes Last Updated By column (who last saved changes on the application)
  - (Recommended) Include Last Updated At timestamp
- Applicant Profile (Autofilled + Editable)
  - Autofill all driver-submitted details
  - Compliance can edit fields for typos/formatting except mobile number (read-only)
- Document Viewer (Multi-file)
  - View all uploaded documents per slot
  - Support preview of JPG/PNG/PDF
  - Clearly show latest replacement uploads for resubmissions
- Compliance Encoding & Verification (Per Document)
  - Compliance encodes and verifies each slot, then sets status Approved/Rejected.
- Driver’s License
  - Encode: License number, license type (Pro/Non-Pro), expiry date (date picker), optional issue date
- OR/CR & Ownership
  - Encode base fields: Plate number, vehicle make, vehicle model, build year, color, registration expiry date
  - Set ownership status: Owned / Not owned / Second hand
  - If Not owned:
    - Require supporting doc: Authorization Letter or Notarized SPA
    - Encode registered owner name
  - If Second hand:
    - Encode transfer doc type (Deed of Sale / Cert of Sale / Cert of Repossession)
    - Encode transfer doc date
- NBI
  - Encode: NBI reference/ID number, NBI expiry/validity end date
- Vehicle Photos
  - Visual check only; status Approved/Rejected (no extra fields)
- PA/CPC (4W)
  - Encode: PA/CPC number, validity/expiry date, optional operator/franchise name
- Fit to Drive Certificate (Conditional)
  - Required if 4W age ≥ 60 OR 2W age ≥ 55
  - Encode: doctor name, clinic/hospital, date of exam, validity/expiry end date (date picker), optional certificate number, optional remarks
- Application Source (Required)
  - Compliance must select application source during verification:
    - Online / Event / Walk-in
  - Required before endorsement
- Reject with Reasons (Sync to Driver App)
  - Reject any document slot with predefined reasons and/or custom reason text
  - Reasons sync to driver app per rejected document slot
- Endorsement Gate
  - System must block Endorse for Activation unless:
    - All required/applicable document slots have a status
    - All required encoded fields are complete
    - Conditional docs satisfied (Fit to Drive when applicable)
    - Application Source selected
- Resubmission Reverification
  - Resubmitted applicants appear in Resubmission tab
  - Compliance reviews replacement documents and may reject again or endorse for activation
- Training Center Management (Shown in Driver App)
  - Compliance/Mobility can CRUD training centers:
    - Name, address, schedule(s), active/inactive
    - Contact number(s) (mobile/landline)
    - Email address
  - Portal can manage Support Contacts shown in the driver app:
    - Hotline number
    - Support mobile number
    - Support email
  - Updates reflect automatically in the driver app Pending Verification screen

---
Assumptions
- Age is computed from Date of Birth and used to determine Fit-to-Drive requirement.
- All mobile onboarding fields are mandatory and validated both client-side and server-side.
- Document upload supports multi-file per slot and enforces accepted types (JPG/PNG/PDF) and 8MB per file.
- Rejection reasons reliably sync to the driver app and map to the correct document slot.
- Training centers and support contacts are centrally configured in the web portal and consumed by the driver app in real time (or near real time).
- “My Applications” tab is a shared operational queue label (not tied to ownership/claiming).

Requirements and Acceptance Criteria
Driver App
Story: As a driver applicant, I want to create my account using mobile OTP with an auto-advance verification flow so that I can start registration quickly with fewer manual steps.
Acceptance Criteria:
- Given the user is on the registration screen, When the user enters a valid mobile number and requests an OTP, Then the app should send an OTP and display the OTP entry screen.
- Given the user is on the OTP entry screen, When the user enters a 6-digit OTP, Then the app should auto-verify the OTP (no manual “Verify” button) and show a loading/validating state.
- Given the entered OTP is correct, When verification succeeds, Then the app should create/verify the account and automatically proceed to the onboarding flow (next screen).
- Given the entered OTP is incorrect, When verification fails, Then the app should show an inline error, clear or allow correction of the OTP field, and remain on the OTP screen.
- Given the OTP is expired (timer ends), When the user taps “Resend OTP”, Then the app should request a new OTP and restart the expiry timer.
- Given the user is on the OTP entry screen, When the user taps “Change Number”, Then the app should return to mobile number entry and invalidate the previous OTP attempt.

---
Story: As a driver applicant, I want to complete my required personal details so that the platform has the minimum information needed to process my application.
Acceptance Criteria:
- Given the user is on the Personal Details screen, When the user proceeds, Then the app should require all fields: full name, date of birth, full address, email, emergency contact name, and emergency contact mobile number.
- Given any required field is blank or invalid, When the user taps Continue, Then the app should show field-level errors and block progress.
- Given all required fields are valid, When the user taps Continue, Then the app should save the details and proceed to the Vehicle Type screen.

---
Story: As a driver applicant, I want to select my vehicle type so that the app can determine the correct next steps and document requirements for my application.
Acceptance Criteria:
- Given the user is on the Vehicle Type screen, When the user selects a vehicle type, Then the app should allow selecting 2W or 4W only.
- Given the user has not selected a vehicle type, When the user taps Continue, Then the app should block progress and show an error indicating vehicle type is required.
- Given the user selected a vehicle type, When the user taps Continue, Then the app should proceed to Service Selection and update the document checklist logic based on the selected vehicle type.

---
Story: As a driver applicant, I want to select the service types I want to apply for so that my application matches the services currently allowed by the platform.
Acceptance Criteria:
- Given the user selected a vehicle type, When the user proceeds to Service Selection, Then the app should show Ride, Send, Eats, Mart.
- Given service availability is restricted by backend configuration, When the screen loads, Then the app should disable or hide unavailable services accordingly.
- Given the user proceeds, When required services/selections are not satisfied by rules, Then the app should block progress and show an appropriate message.

---
Story: As a driver applicant, I want to see a document checklist based on my submitted information so that I know exactly which documents I need to complete my application.
Acceptance Criteria:
- Given the user has entered Personal Details + Vehicle Type, When the Documents screen loads, Then the app should display the required document slots based on rules (vehicle type and any conditional requirements such as Fit-to-Drive thresholds, ownership conditions, etc.).
- Given a condition changes (e.g., ownership type selection), When the user updates the condition, Then the app should dynamically show/hide the affected required document slots.
- Given required documents are missing, When the user attempts to submit, Then the app should block submission and clearly indicate which document slots are incomplete.

---
Story: As a driver applicant, I want to view document guides with instructions and examples so that I can upload compliant files and avoid rejection.
Acceptance Criteria:
- Given the user is on the Documents screen, When the user views any document slot, Then an info (ℹ️) icon must be available for that document type.
- Given the user taps the info icon, When the guide opens, Then the app should show:
  - clear instructions (what to capture / common rejection reasons),
  - accepted file types and size limits,
  - and example images (at least “good” vs “bad”).
- Given the guide is open, When the user closes it, Then the user should return to the same document slot without losing progress.
- Given the user is in Pending Review or Resubmitted Successfully states, When the user opens a guide (if exposed), Then it must be read-only and must not allow uploads from within the guide.

Story: As a driver applicant, I want to upload my documents with clear file rules so that I can submit the correct files successfully.
Acceptance Criteria:
- Given the user is on the Documents screen, When the user uploads files to a document slot, Then the app should support multiple files per slot where applicable.
- Given the user selects an unsupported file type, When the upload is attempted, Then the app should reject the file and show an error (accepted: JPG/PNG/PDF).
- Given the user selects a file larger than 8MB, When the upload is attempted, Then the app should reject the file and show an error (max 8MB each).
- Given a file uploads successfully, When the upload completes, Then the app should show the file name in the uploaded list for that slot.

Story: As a driver applicant whose documents were rejected, I want to see which files were rejected and why so that I know what needs to be corrected.

- Given the application status is Rejected / Needs Reupload, When the user opens the status screen, Then the app should show which document slots are rejected and the rejection reason per slot.

Acceptance Criteria:

- Given a file is listed in the summary, When the user taps the file name, Then the app should open a viewer showing the actual uploaded image/PDF in read-only mode (no replace/delete/upload).
